# go-web-openapi

Generate the React application's TypeScript client from the Go
service's OpenAPI description.

## Why

The React application and the Go API must not drift apart; a typed
client generated from one description keeps them in step.

## Scope

The description is done: `webapi/openapi.yaml` (OpenAPI 3.1), checked
against the route table by `webapi/internal/server/openapi_test.go`
(each route described, each described operation served unless marked
`x-tgd-status: planned`), with `webapi/README` and `web/docs/`
pointing at it as the API contract. Left, in `web/app/`:

- The generated client goes to `web/app/src/api/generated/`,
  committed, regenerated by `npm run gen:api` from
  `webapi/openapi.yaml` with openapi-typescript (types) and
  openapi-fetch (typed fetch), versions pinned in
  `web/app/package-lock.json`. The application calls the API only
  through it, and its hand-written shapes (`src/types.ts`, the props at
  the top of `src/routes/*.tsx`) give way to the generated schemas.
- A check that regenerating the client from the description gives no
  diff.

## Design notes

- No network at build time: the generator runs from a pinned image or
  a vendored tool.
- Operations marked `x-tgd-status: planned` are not served by the Go
  service yet (they answer 404 there); the stand-in answers them.
- The page data of `GET /api/page/{path}` is a `oneOf` over the
  routes, told apart by the `route` enum of each variant; there is no
  `discriminator` object, since several route ids share one props
  schema.
- The CSRF tokens are the `csrf` and `loginCsrf` security schemes, not
  header parameters, so a middleware can add `X-CSRF-Token` and the
  calls need not pass it.

## Depends on

Nothing.

## Done when

- The generated client compiles, the application calls the API only
  through it, and regenerating it gives no diff.
